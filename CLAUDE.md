# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Sport Timer is a Flutter interval timer for workouts (preparation, round, rest, number of rounds). Platforms: Android, iOS, macOS.

## Commands

The Flutter version is pinned in `.fvmrc`. Always use `fvm flutter` / `fvm dart`, never bare `flutter` or `dart`.

```bash
fvm flutter pub get
./rebuild.sh                         # clean + pub get
fvm flutter analyze
fvm flutter run                      # entry point is lib/main.dart
fvm flutter test                     # all tests
fvm flutter test test/features/timer # one folder or file
fvm flutter test --update-goldens test/snapshots/ui_snapshots_test.dart # refresh UI snapshots
fvm dart tool/agent_check.dart       # only the checks the changed files need (see below)
fvm dart tool/dispatcher.dart next   # which project task can start now (also: models, launch <ID> --tool=<tool>, status)
```

`tool/agent_check.dart` compares the working tree with `master` (`--base=<branch>` changes it, `--skip-build` skips the debug builds, or pass file paths to check only those). From the changed paths it picks: `dart format` (check only), `flutter analyze` on those files, the mirrored tests plus the layer boundary test, the golden snapshots when a presentation file, `navigation.dart` or an ARB file changed, `gen-l10n` when an ARB file changed, `test/architecture/ai_setup_test.dart` when `CLAUDE.md`, `.agents/`, `.claude/` or `.codex/` changed, the debug builds when `android/`, `ios/` or `pubspec.yaml` changed, and a scan of the added lines for local absolute paths (a failure) and open notes (only listed). With file paths, every line of each file counts as added. The rules are in `ChangeSet` and are tested in `test/tool/agent_check_test.dart`. It adds to the full `fvm flutter test` run, it does not replace it. A change to domain, data or built-in template code can still alter a screen, so run the snapshot test by hand then.

`.zed/tasks.json` (tracked in git; the other `.zed/` files are local symlinks and stay excluded) wraps run, pub get, rebuild and test as Zed tasks.

Tests live under `test/` and mirror `lib/`. The CI workflow (`.github/workflows/ci.yml`) runs `flutter analyze` and `flutter test` on every pull request.

UI snapshot goldens (`test/snapshots/goldens/*.png`) and their flow index (`test/snapshots/README.md`) are generated by `test/snapshots/ui_snapshots_test.dart` using Alchemist platform goldens on macOS. Any UI change that alters a captured screen, state, or route transition must refresh the affected snapshots (`fvm flutter test --update-goldens test/snapshots/ui_snapshots_test.dart`) and update the flow links in `test/snapshots/README.md`.

## Project layout

Feature-first layout with MVVM (see the next sections), `get_it` for DI (registered by hand) and `go_router` for navigation. There is no code generation: a fresh clone needs only `fvm flutter pub get`.

```
lib/
  main.dart, firebase_options.dart, navigation.dart
  di/di.dart                    composition: registers the implementations
  l10n/                         generated localizations (l10n.yaml points here)
  core/                         pure Dart: Result, extensions/duration_extension.dart
  shared/presentation/          shared UI: theme/ (style tokens, SportTheme), extensions/ (l10n_context, theme_context, text_theme_extension), widgets/ (app_button, app_surface)
  features/<name>/
    domain/                     models and contracts (pure Dart)
    data/                       implementations that use platform packages
    presentation/               ViewModel, state, pages, widgets
```

A feature has only the layers it needs. Features: `user` (domain, data), `login`, `account`, `home` (presentation only), `settings`, `templates`, `timer` and `statistics`.

- `main.dart` holds `main()` and `MyApp`. It initializes Firebase, then calls `configureDependencies()` before `runApp`.
- `user`: the `UserRepository` contract returns the app's own `AppUser`, not a Firebase type. `FirebaseUserRepository` (data) maps the Firebase user with the `toAppUser()` extension. `login` and `account` have a ViewModel, state and pages in their presentation layer.
- `settings`: models (`TimerSettings`, `TimerConfiguration`, `TimerStyle`) and the `SettingsRepository` contract are in domain. `SharedPreferencesSettingsRepository` (data) stores them in `SharedPreferences`. The setup page and the timer styles page are in presentation. `HomePage` creates one `SettingsViewModel` and shares it with its tabs.
- `templates`: `WorkoutTemplate` and the built-in templates are in domain. The templates page, its ViewModel and `TemplateTile` are in presentation.
- `timer`: `TimerParams`, `TimerSchedule`, `TimerStatus` and the `AudioManager` and `BackgroundKeepAlive` contracts are in domain. `DefaultAudioManager` and `DefaultBackgroundKeepAlive` (data) play sounds and keep the app alive with the screen off. The timer ViewModel, state, page and style views are in presentation. `TimerPage` uses `wakelock_plus` directly (the one documented exception to the platform rule).
- `statistics`: session models and the `ActivityAccountSource` contract are in domain. The `sqflite` database (`activity.db`), `ActivityAccess` and the Firebase account source are in data. The statistics page owns a `StatisticsViewModel` and displays account-scoped daily totals.
- `navigation.dart` defines the routes (`/` login, `/home`, `/timer`, `/timer-styles`, `/templates`) and passes the `TimerParams` from `state.extra` to `TimerPage`. Each page creates and disposes its own ViewModel.
- `lib/di/di.dart` is the composition point. It registers the app-wide singletons by hand: `AudioPlayer`, the repositories, `AudioManager`, `BackgroundKeepAlive` and the activity database. ViewModels are not registered. Keep the registration order, because `ActivityAccess` is closed before `ActivityDatabase`.
- `lib/core/` holds the sealed `Result<T>` (`Success` and `Failure`, with `fold`) and the `Duration` extension (`asMinutesAndSeconds`). Repositories return `Result` from the methods that can fail, and the ViewModels turn it into state. Logging uses `debugPrint`.

## Architecture (MVVM and layers)

Dependencies point inward: presentation depends on domain, and data depends on domain. Domain depends on nothing else.

- **Domain** (`features/<name>/domain/`): models and repository or manager contracts. Pure Dart: only `dart:*`, `core/` and the domain files of other features. No Flutter, no platform package, no data or presentation import. Contracts return app types (`AppUser`), never platform types. A contract that needs a callback declares its own `typedef` (`KeepAliveAction`) instead of using `VoidCallback`.
- **Data** (`features/<name>/data/`): implements the contracts and wraps platform APIs (`FirebaseAuth`, `SharedPreferences`, `sqflite`, `AudioPlayer`). It never imports presentation. It maps platform types to domain types before returning them.
- **Presentation** (`features/<name>/presentation/` and `shared/presentation/`): ViewModels, state, pages and widgets. It never imports data files or platform packages. It gets implementations from `getIt<T>()` where the page creates its ViewModel, and it types them by their domain contract.
- **View**: a page or widget. It reads the ViewModel state, calls its methods, does navigation (`go_router`) and shows snackbars. It never calls a repository.
- **ViewModel**: one per screen or feature. It holds the state, calls repositories and managers, and owns timers and side effects such as sounds. It never imports widgets or `BuildContext`, so it can be unit tested without a widget tree.
- **Extensions**: a helper that works on one type (its first argument is the thing it works on, or it maps one type to another) must be an extension, never a top-level function. One extension per file, in an `extensions/` folder of the layer it belongs to: `core/extensions/` (pure Dart), `shared/presentation/extensions/`, or `features/<name>/<layer>/extensions/`. It follows the rules of that layer (a mapper from a platform type lives in `data/extensions/`). A top-level function is only for work no single type owns, like `main()`. The boundary test does not check this; review does.
- **Shared code**: UI used by several features (theme, localization helper, `AppButton`, `AppSurface`) is in `shared/presentation/`. Pure helpers used by several features are in `core/`. Code used by one feature stays in that feature, even if another feature could use it later.
- **Composition**: only `main.dart`, `di/di.dart` and `navigation.dart` may know both a contract and its implementation.
- **Use cases**: do not add them by default. Add one only when there is real business logic, or logic that several ViewModels reuse. A class that only forwards a call to a repository is not allowed.

Rules:

- Repositories return a `Result` (a sealed class with a success and a failure case), so the caller must handle errors. The ViewModel turns the `Result` into state (data, error message, loading flag). A View never sees a `Result`.
- A ViewModel method that the View must react to once (sign in, save) returns `Future<bool>`. The View awaits it and then navigates or shows the snackbar. Do not put one-time events in the state.
- Navigation stays on `go_router`. `lib/navigation.dart` creates each page and passes route params (`state.extra`) to the ViewModel constructor.
- `get_it` holds only app-wide singletons: repositories, managers and `AudioPlayer`. They are registered by hand in `lib/di/di.dart`, with no `injectable`.
- ViewModels are not registered in `get_it`. The page creates its ViewModel and takes its dependencies with `getIt<T>()` at that point. A ViewModel shared by several widgets is owned by their closest common parent and passed down through constructors.
- Feature-first layout: no `part` files, no barrel libraries, no generated files. Use normal imports.

### Boundary check

`test/architecture/layer_boundaries_test.dart` reads the `import`, `export` and `part` lines of every file under `lib/` (both URIs of a conditional import) and the file paths, and fails when a rule above is broken:

- domain imports anything but platform-free `dart:*` libraries (not `dart:ui`, `dart:io`, `dart:html`, `dart:js*`, `dart:ffi`, `dart:isolate`), `core/` and domain files;
- presentation imports data files or platform packages (`firebase_*`, `google_sign_in`, `sqflite`, `shared_preferences`, `audioplayers`, `audio_service`, `permission_handler`, `wakelock_plus`);
- data imports presentation;
- `core/` imports Flutter, features, shared or a platform `dart:*` library;
- any file uses `part` or `part of`;
- a file under `lib/features/<name>/` is outside `domain/`, `data/` and `presentation/`, or a file under `lib/shared/` is outside `presentation/`. Top-level files (`main.dart`, `navigation.dart`, `firebase_options.dart`, `di/`, `l10n/`, `core/`) are exempt.

The one import exception is `wakelock_plus` in `timer_page.dart`, listed with its reason in the test. A new exception must be added there with a reason. It runs with `fvm flutter test`, so CI covers it.

The check cannot see `getIt` calls in a View, a View using a repository it received another way, imports between features, or a domain class using a type that reached it through an allowed import. Those stay a review job.

## Styling and theme

All screens share one look. Use the shared pieces in `lib/shared/presentation/`; do not draw your own copy. The goldens in `test/snapshots/goldens/` are the visual reference, so no emulator is needed to check a style change.

- **Tiles and cards**: use `AppSurface` (`widgets/app_surface.dart`) for any bordered tile, tappable or not. It owns the fill, the 12 radius, the 1px `outlineVariant` border and the selected state (2px primary border, with the padding shrunk so the size does not change). Never hand-build a `Material`, `Ink` or `Container` with a border for a tile.
- **Radius and border width**: only `AppRadius` (r8 small inner items, r12 tiles and buttons, r20 sheets and dialogs) and `AppBorderWidth` (thin 1, thick 2). No raw `BorderRadius.circular(12)` or border-width numbers. The exceptions are circles, pills (phase chip, phase bar, rounds strip), the timer style preview frame, the picker items' phase-colored border, and the theme definitions in `SportTheme`.
- **Buttons**: use `AppButton` (`primary`, `secondary`). The 12 radius shape comes from the button themes in `SportTheme`, so never set a shape on one button. To change the size, padding, text or icon of one button, pass `style:` to `AppButton`: it is merged over the app theme, so the shape stays. Never wrap an `AppButton` in a local `FilledButtonTheme` or `OutlinedButtonTheme`, because that replaces the app theme instead of merging. Dialogs and bottom sheets take their radius from `SportTheme` too.
- **Text**: for the shared roles use `AppTextThemeExtension` on `TextTheme` (`tileTitle`, `tileSecondary`, `tileValue`, `emphasizedLabel`) and set the color at the call site. Timer and picker digits use `AppTextStyles`. A style that is used in 2 or more places gets a getter there, instead of repeating `titleMedium.copyWith(fontWeight: ...)`.
- **Colors and alpha**: colors come from the theme (`colorScheme`, `context.timerColors`, `AppPalette`). Shared alpha values are `AppAlpha` and `TimerAlpha`. No `Color(0x...)`, `Colors.*` or raw `withValues(alpha: 0.x)` in a widget.
- **Before adding a style**: check these pieces first. A new shared token or widget needs 2 or more users. Remove a token or widget when nothing uses it anymore.
- Any change that alters a captured screen refreshes the goldens, as described under Commands.

## State management

State is held with `ValueNotifier`. There is no state management package.

- In every class, the fields come first, then the constructor, then the methods.
- Each ViewModel has a private `ValueNotifier<XState>`, exposed as `ValueListenable<XState> get state`. Only the ViewModel changes it, with `_state.value = _state.value.copyWith(...)`.
- `XState` is a plain immutable Dart class: `final` fields, a `const` constructor, `copyWith`, `==` and `hashCode`. `ValueNotifier` only notifies when the new value is not equal to the old one, so `==` is required. No `freezed`.
- Views read state with `ValueListenableBuilder`. To rebuild only part of a screen, build a smaller `ValueListenable` from the state for that widget.
- The ViewModel has a `dispose()` that cancels timers and subscriptions and disposes the notifier. The `State` of the page that created the ViewModel calls it from its own `dispose()`.
- Async methods check a `_disposed` flag before setting state, because the page can be gone when the work finishes.
- Test ViewModels with unit tests and hand-written fake repositories. No `bloc_test`, no mocking package unless it is added on purpose.

## Dependencies and Android build

- All versions in `pubspec.yaml` are pinned exactly, with no `^`. Keep it that way when adding packages.
- The Android build uses Gradle 9.3.1, AGP 9.1.0 and Kotlin 2.4.0. `firebase_core` and `firebase_auth` still apply the old Kotlin Gradle plugin, so `android.builtInKotlin=false` in `android/gradle.properties` must stay until they migrate. The "plugins that apply KGP" warning during the build is expected.
- Firebase config (`lib/firebase_options.dart`, `android/app/google-services.json`, `ios/Runner/GoogleService-Info.plist`) is generated by `flutterfire configure` for the `sport-timer-503e8` project.

## Workflow

To plan work into tasks that runners can implement without asking anything, use `.agents/skills/skill-planner/SKILL.md`. It interviews the user, asks the view questions for UI work, builds an HTML mockup the user approves, proposes the acceptance criteria, and checks each task with a fresh reader. The task format is in `.agents/rules/project-tasks-format.md`.

For an end-to-end change (bug, feature, improvement, refactor), read and follow `.agents/skills/skill-orchestrator/SKILL.md`. This is the single repo-local skill folder shared by Claude, Codex and Antigravity. Never use `skill-ticket-orchestrator` here: this project has no tickets and no Linear. Follow the skill's approval cadence for implementation, review, commit and PR.

To run tasks that are already planned in `project-tasks/`, with no questions asked while they run, use `.agents/skills/skill-dispatcher/SKILL.md`. It starts one runner per task (implementer, tests, review, each with its own model) in a clean clone through `tool/dispatcher.dart`. Under that skill the script (not the runners) commits, pushes the task branch and opens the PR without asking; the script never pushes to `master` and never merges.

To handle the review comments the user left on their own PR, use `.agents/skills/skill-pr-feedback/SKILL.md`. The comments are discussed in chat, then the skill reviews the fixes, commits, pushes the PR branch and posts a short status reply in each comment thread. It commits, pushes and posts without asking again, because the user starts it for that.

## AI tools setup (Claude, Codex, Antigravity)

All three tools must behave the same. Every rule and role is defined once; each tool only gets a thin file that points to it.

| What | Single source | Tool files |
| --- | --- | --- |
| Instructions | `CLAUDE.md` (real file) | `AGENTS.md` (Codex) and `GEMINI.md` (Antigravity) are symlinks to it |
| Rules | `.agents/rules/` | `.claude/rules` is a symlink to it; Antigravity reads it directly |
| Skills | `.agents/skills/` | `.claude/skills/*` are symlinks; Codex and Antigravity read the folder directly |
| Agent roles | `.agents/skills/skill-orchestrator/roles/<name>.md` (model, effort and access in its frontmatter) | none |
| Codex model carrier | `.codex/agents/*.toml` | only name, description, model, effort and one line that points to the role file |

Claude and Antigravity need no agent files: Claude passes the role file's model and effort to a general-purpose agent, and Antigravity runs the role in the main thread by reading the role file. Edit the single source, never copy a rule into a shim or a skill. Read `.agents/rules/dart-style.md` before you read, write or review any Dart code (it wins over the shared Dart rules), `.agents/rules/git-commits.md` before you create a branch, write a commit message or write a PR title, and `.agents/rules/project-tasks-format.md` before you read, create or change a task under `project-tasks/`.

What stays tool-specific: Claude hooks and auto memory, and how a skill is started (Claude `/skill-orchestrator`, Codex `$skill-orchestrator`, Antigravity by naming the skill). `test/architecture/ai_setup_test.dart` guards this setup.
