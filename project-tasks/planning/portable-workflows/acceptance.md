# Proposed acceptance criteria

These are proposed observable criteria awaiting user approval. Test filenames below are planned outputs, not existing or already-passing tests. Detailed tasks must assign each criterion to its implementation and assembled verification owner. The generic Python package initially lives under `tool/plan_dispatcher/`; Sport Timer parity data/tests stay outside it.

- [ ] R1: When installed in a macOS project with supported Python, then setup installs project-local skills/runtime, clearly defaults to all three supported tools, allows a subset and preserves unrelated/global files. Check: planned `test_install.py` install/ownership cases.
- [ ] R2: When setup finds project tooling, then it proposes setup/check commands for one confirmation and saves the approved configuration; dispatch does not invent helper scripts or runners. Check: planned `test_install.py` discovery/confirmation and `test_lifecycle.py` frozen-plan cases.
- [ ] R3: When restoring or explicitly updating an installation, then the pinned local-source/release version is reproducible, updates protect active runs/user modifications and failed updates roll back. Check: planned `test_install.py` restoration and `test_update.py` transaction cases.
- [ ] R4: When choosing work, then only valid ready tasks with completed dependencies, supported capabilities/executor and no reservation/PR/path conflict are eligible; cycles, unknown dependencies and lookup failures are explained. Check: planned `test_selection.py` and `test_reservations.py` eligibility/error cases.
- [ ] R5: When no task is named, then dispatch recommends an eligible task and waits for launch approval; an explicit eligible task request skips duplicate selection approval. Check: planned `test_dispatcher_skill.py` coordinator scenarios.
- [ ] R6: When choosing execution settings, then task-appropriate available CLI models are recommended, manual overrides work and automatic selection applies only to the current approved run/thread; unavailable explicit choices never silently change. Check: planned `test_models.py` recommendation/authorization cases.
- [ ] R7: When invoked from T3, a supported CLI or an unknown IDE, then execution always uses the selected installed provider CLI, unknown environments save a local choice and doctor reports missing prerequisites before coding. Check: planned adapter tests, `test_preflight.py` and `test_dispatcher_skill.py` cases.
- [ ] R8: When a task starts, then it receives a fresh external clone/task branch without changing the active checkout, and atomic shared reservations prevent duplicate/overlapping launches across linked worktrees. Check: planned `test_workspace.py` and `test_reservations.py` Git fixtures.
- [ ] R9: When executing an approved task, then one worker implements/tests, fresh independent review follows, at most two fresh repair invocations address checks/review together and only major unresolved issues stop execution. Check: planned `test_lifecycle.py` repair/review/report/denial cases.
- [ ] R10: When checking work, then the shared Python checker supports frozen run and developer modes, ordered checks, file mapping, optional build groups and failure/advisory added-line scans, without broadening a run's permissions through edited configuration. Check: planned `test_checks.py`, `test_diff.py` and consumer parity tests.
- [ ] R11: When retiring Sport Timer's validator, then Python configuration matches its existing changed-file/explicit-file/base/build/localization/snapshot/architecture/scan behavior and developer consumers use the new checker. Check: shared parity table and planned `test_plan_dispatcher_parity.py`, plus retained Flutter tests.
- [ ] R12: When publishing, then task archive/notes changes are included before final checks/review, the pushed SHA equals the verified candidate, retries reuse the same PR and only the authorized task branch is pushed. Check: planned `test_publication.py` candidate/idempotence/branch/privacy cases.
- [ ] R13: When required checks, permissions or major findings cannot be resolved, then work/results/reservation stay local without a WIP push and resume continues the saved stage; a replacement thread needs explicit handover and fresh model approval. Check: planned `test_lifecycle.py` blocked/resume/adopt cases.
- [ ] R14: When publishing succeeds, then the task clone is removed automatically; cleanup failure preserves publication success with a warning, and active/blocked reservations are never reclaimed merely by age. Check: planned `test_cleanup.py` and `test_reservations.py` cases.
- [ ] R15: When planning tasks in any project, then the shorter task format retains relevant contracts, interview completeness checks, approved UI mockups, agreed criteria and independent task cold reads using configured project rules. Check: planned `test_planner.py` workflow/asset/command scenarios.
- [ ] R16: When cutting Sport Timer over, then skills/old runner/test assertions change atomically, backlog content moves to docs/tasks without loss, executor boundaries remain explicit and every intermediate PR preserves the app/checks. Check: planned setup assertions, backlog/link validation, Python tests and required Flutter checks per cutover task.
- [ ] R17: When extracting, then public GitHub alexaniko88/plan-dispatcher starts with a fresh MIT commit containing only generic sources/notices, and a Sport Timer completion PR records the immutable release before adoption. Check: planned export-tree validation, GitHub release/commit evidence and source task archive validation.
- [ ] R18: When adopting the release, then Sport Timer restores that pinned package before temporary sources are removed, rollback preserves the backlog, and temporary non-Flutter consumers prove install/lifecycle portability and are deleted. Check: planned `test_release_install.py` and `test_portable_flow.py` (renamed from `test_non_flutter_flow.py` so the package-boundary scan stays clean); separate live Codex worker/reviewer fixture smoke, with absent-provider evidence explicitly unverified.

The future dispatcher launch authorizes task commits/push/PR creation without further routine questions. It never merges, force-pushes, pushes to the base branch, posts GitHub comments or sweeps unrelated local branches. Planner publication still follows its own final approval. These limits must be checked in publication/coordinator tests and visible in the canonical workflow assets.
