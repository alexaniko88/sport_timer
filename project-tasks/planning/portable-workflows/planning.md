# Portable planner and dispatcher

## Original request

Simplify the dispatcher and its linked execution process, especially permissions. Make the planner and dispatcher independent of Flutter so they can be extracted into a separate reusable project. Plan the complete simplification and migration as executable backlog tasks through skill-planner. First remove project coupling in Sport Timer; extraction follows afterward.

The dispatcher must choose an eligible task itself and skip blocked tasks. The user asked whether the Dart tools should become shell scripts and whether every existing tool is still necessary. Accepted refinements include Python, one worker plus independent review, retained blocked work, automatic publishing authorized at launch, and successful-workspace cleanup. The decisions below supersede earlier unaccepted suggestions.

## Decisions

- D1 (user-chosen): the planner and dispatcher must become reusable across projects, independent of Flutter, with a separate project as the intended destination.
- D2 (user-chosen): the dispatcher chooses workable tasks and does not select blocked tasks.
- D3 (user-chosen): focus first on removing Flutter coupling; migration/extraction is the next stage, and this planning effort covers both stages.
- D4 (user-chosen): use skill-planner to interview, define acceptance and produce the required backlog; implementation is outside this planning session.
- D5 (accepted recommendation): use Python for the reusable engine, with Flutter commands supplied through Sport Timer project configuration. The engine itself must not depend on Flutter or FVM.
- D6 (user-chosen): execution must adapt to the invocation environment. Detect whether delegation through a host such as T3 is available; when unavailable, use execution appropriate to the invoking CLI (Claude, Codex or Antigravity). T3 must not be a required dependency. Detection and model/provider selection details remain open; this decision does not authorize switching providers after a failed or denied operation.
- D7 (user-chosen): recommend provider and model according to the selected task. The user can switch manually or approve the dispatcher applying the recommendation automatically. A recommendation is not authorization to switch. Approval scope remains open.
- D8 (user-chosen): invocation must also work from IDE agent environments such as Zed's agent panel, Antigravity and Cursor, as well as standalone CLIs. Adapt to available execution capabilities rather than assuming every invocation is one of three standalone CLIs. Specific supported integrations and verification boundaries remain open.
- D9 (accepted recommendation): first-version execution integrations are T3 and the Claude, Codex and Antigravity CLIs. Other environments use simple manual configuration of a supported execution route; do not build bespoke integrations for every IDE. Keep unknown-environment setup as simple as possible. Custom execution commands or plugins have not been approved.
- D10 (accepted recommendation): in an unknown environment, ask the user to choose Claude CLI, Codex CLI or Antigravity CLI, verify availability, and save that execution choice locally for the project so subsequent invocations do not repeat setup. Users need not write adapters or shell commands. This saved choice does not authorize provider/model changes or publishing.
- D11 (user-chosen): offer automatic application of provider/model recommendations for the current session. The user asks whether session means the current thread; define the session as that conversation/thread, not the saved project execution choice. This grants model/provider selection only, not permission expansion or publishing. Identification in CLI environments without an exposed thread id remains a design detail to resolve.
- D12 (accepted recommendation): use a coordinator that selects and launches tasks, one task worker owning implementation and tests through validation, and a fresh independent reviewer for each task. The same task worker handles actionable review fixes with bounded retries; the exact retry bound remains open. Do not create separate implementation and test agents or require nested subagents. Execution adapters use supported delegation or separate CLI runs as appropriate. Keep review consistent for small tasks in the first version rather than adding complexity-based exemptions.
- D13 (user-chosen): launching a planned task authorizes committing, pushing its task branch and opening its PR without another approval checkpoint. Routine implementation choices and minor issues should not interrupt execution. Stop only for major blockers; their precise definition remains open. This is a requirement for the future dispatcher, not approval to publish this planning branch or bypass runtime permission denials.
- D14 (accepted recommendation with user emphasis): major blockers are consequential missing decisions, unavailable required permissions, unresolved failing required checks, or serious review findings after attempted fixes. Minor findings are reported in the PR without stopping. The planner must resolve foreseeable decisions and validate execution requirements before marking tasks ready so blocked runs are exceptional, not the normal process. Unexpected runtime failures remain possible; readiness is not permission to bypass denials or publish failed work as verified.
- D15 (user-chosen): one task per conversation/thread. The dispatcher must not start a queue or launch additional tasks in the same thread; the user manually opens another thread for another task. Different threads may run concurrently, so shared task reservation and overlap protection are still required. D11 automatic model selection applies to this thread's task stages and retries; it does not imply a multi-task loop.
- D16 (accepted recommendation): on a major blocker, retain the task workspace and results locally for resume in the same thread. Replace the current automatic failed-run WIP push and cleanup with this retained local state. Successful-run cleanup was subsequently settled by D27.
